# MirrorPlay 键鼠映射引擎 · 详细设计

> 配套文档：《免会员手游投屏软件开发方案》v1.2（4.6 节的展开）
> 版本 v1.0，最后更新 2026-09
> 阅读对象：负责本模块的客户端开发、测试

---

## 一、模块定位

### 1.1 它为什么是核心

投屏本身是"scrcpy 已经解决的问题"，GUI 是"体力活"。真正决定这个产品能不能打的，只有键鼠映射引擎——这也正是 TC Games 拿来当 VIP 卖点、且免费版只给"行走/射击/开火/普通点击"四类基础映射的原因。

本模块的目标：**把 TC Games VIP 的全部映射类型做全、做顺手，并且永久免费**。

### 1.2 设计目标

| 目标 | 指标 |
| --- | --- |
| 延迟 | 键鼠事件从按下到注入设备 ≤ 15ms |
| 精度 | 跨分辨率（720P ↔ 1080P ↔ 2K）坐标误差 < 1% |
| 并发 | 同时维持 ≥ 4 个"手指"（左手摇杆 + 右手视角 + 开火 + 技能）互不干扰 |
| 手感 | 视角控制支持灵敏度、死区、加速度曲线，可调到"像端游" |
| 可扩展 | 新增映射类型不改引擎主体，只加一个 Strategy |

### 1.3 明确红线

- 只做**输入设备转换**：把键鼠事件翻译成触摸事件，1:1 对应人的操作意图。
- **不做**自动瞄准、自动压枪、透视、自动打怪、基于图像识别的自动决策。
- 宏（macro）是**用户显式录制/编写的多步序列**，必须有速率上限与"需持续按键"约束，禁止无人值守循环——这是与外挂的分界线，详见第九节。

## 二、总体架构

```
┌─ 输入采集层 ──────────────────────────────────────────┐
│  KeyboardHook (Raw Input / LowLevelKeyboardProc)      │
│  MouseHook    (Raw Input 相对位移 + 绝对坐标)          │
│  → 统一成 InputEvent{type, code, state, dx, dy, ts}   │
└────────────────────┬──────────────────────────────────┘
                     │ 无锁环形队列（单生产者）
┌────────────────────▼──────────────────────────────────┐
│  映射引擎 MappingEngine（独立线程，高频）              │
│   ├ KeyRouter    : 键 → MappingItem（O(1) 查表）       │
│   ├ Strategy     : 每个类型一个状态机（见第五节）      │
│   ├ CoordMapper  : 窗口坐标 → 相对坐标 → 设备坐标      │
│   ├ PointerPool  : pointer id 分配 / 回收 / 超时       │
│   └ EventMerger  : 同帧多点 move 合并                  │
└────────────────────┬──────────────────────────────────┘
                     │ Gesture{action, pointerId, x, y, ts}
┌────────────────────▼──────────────────────────────────┐
│  注入层 Injector                                       │
│   ├ 节流：按注入频率（默认 60~120Hz）对齐              │
│   ├ 序列化：控制协议消息                                │
│   └ 发送：走 ADB control socket → 设备端 inject        │
└────────────────────────────────────────────────────────┘
```

线程模型：**采集线程 → 引擎线程 → 注入线程**，三段分离，任何一段阻塞都不影响其他两段。队列用单生产者单消费者无锁环形缓冲，避免锁竞争引入抖动。

### 2.1 为什么采集要用 Raw Input

- 鼠标：需要**未受操作系统加速处理的原始相对位移**，否则视角手感会被 Windows 指针加速污染。Raw Input 的 `RIDEV_NOLEGACY` 可拿到原始 dx/dy。
- 键盘：需要区分**物理按键**（`VK_` 用扫描码映射），避免输入法/键盘布局差异导致键位错乱；同时要能拿到按键的重复（repeat）状态并自行处理（见 5.1）。

## 三、坐标系统（最容易出错的地方，先定死）

一条坐标要穿过四层，任何一层搞错都会表现为"点击位置偏了"。

```
① 窗口像素 (wx, wy)     鼠标在投屏窗口内的位置
        ↓ CoordMapper.windowToRelative()
② 相对坐标 (rx, ry)     0~1，与分辨率/DPI 无关 ★ 持久化只用这一层
        ↓ CoordMapper.relativeToDevice()
③ 设备渲染坐标 (dx, dy) 设备当前实际分辨率（含旋转）
        ↓ 设备端注入
④ 游戏内 UI 坐标
```

**持久化只用相对坐标**：映射脚本 JSON 里存的永远是 0~1。这样同一份键位在 720P、1080P、2K 手机上都不跑偏——这是 4.6 数据模型里 `pos: {x: 0.82, y: 0.61}` 的原因。

### 3.1 窗口 → 相对坐标（要减掉黑边）

投屏窗口为了保持宽高比常带黑边（letterbox），直接拿窗口坐标算会偏移。

```
// 已知：窗口客户区 wndW×wndH，视频实际显示区 videoRect{x,y,w,h}
rx = (wx - videoRect.x) / videoRect.w
ry = (wy - videoRect.y) / videoRect.h
// clamp 到 [0,1]，超出黑边区域的点击直接丢弃
```

支持的三种填充模式（对应主方案 4.4 的窗口设置）：

| 模式 | videoRect 计算 | 点击边界外 |
| --- | --- | --- |
| 等比（contain，默认） | 居中留黑边 | 丢弃 |
| 拉伸（stretch） | 铺满窗口 | 允许，但坐标被拉伸 |
| 裁切（cover） | 铺满并裁掉溢出部分 | 丢弃 |

### 3.2 相对坐标 → 设备坐标（要处理旋转）

```
// 设备当前宽高（已考虑旋转）
if (rotation == 90 || rotation == 270) { devW = H; devH = W; } else { devW = W; devH = H; }

dx = rx * devW
dy = ry * devH
```

**关键坑**：设备端注入用的是**设备当前坐标系**。游戏横屏时设备本身可能处于 portrait 旋转态，需要读取设备实际 rotation 后再换算。M1 阶段就要把旋转变化做成事件监听（设备转屏时重算所有 active pointer 的位置）。

### 3.3 视频分辨率 ≠ 设备分辨率

投屏时为降带宽会做 `--max-size` 缩放，视频帧是 720P 但设备是 1080P。因为中间层用相对坐标，这个差异被天然吸收——这也是必须用相对坐标的第二个理由。

### 4.1 字段设计要点

- `schema` 版本号：**必须**。后续加字段/改语义时靠它做迁移，否则老键位文件会静默失效——这是所有脚本化功能最容易埋的雷。
- `target.w/h`：只用于编辑器里的背景标尺显示，**运行时不参与计算**（运行时一律走相对坐标）。
- `id`：每个 item 稳定唯一，用于 pointer 绑定与冲突检测。
- `switchKey`：必备。玩手游时经常需要短暂回到普通触控（比如拖背包、点菜单），一键切换是刚需。

### 4.2 冲突检测规则（编辑器实时校验）

| 冲突类型 | 处理 |
| --- | --- |
| 同一按键绑定多个 item | 报错，要求改键（视角 + 开火 分属不同键，不冲突） |
| 两个 steering/view 抢占同一屏幕区域 | 警告（可能互相吞事件） |
| macro 与 click 同键 | 报错 |
| 绑定到系统保留键（如 `switchKey` 自身、Alt+F4） | 报错 |

## 五、映射类型：状态机与算法

每种类型实现同一个接口：

```cpp
class IMappingStrategy {
public:
    virtual void onKeyDown(const KeyEvent& e) = 0;
    virtual void onKeyUp(const KeyEvent& e)   = 0;
    virtual void onMouse(const MouseEvent& e) = 0;   // 含相对位移 dx/dy
    virtual void onTick(int64_t nowMs)        = 0;   // 引擎主循环驱动，用于持续型手势
    virtual void onReset()                    = 0;   // 切换模式/断连时强制归位
};
```

### 5.1 通用：按键去抖与 repeat 处理

Windows 长按会持续发 keydown。引擎必须自行维护按键状态表：

```
onKeyDown(k): if (keyState[k]) return;   // 忽略 repeat
              keyState[k] = true; dispatch(k, DOWN);
onKeyUp(k):   if (!keyState[k]) return;
              keyState[k] = false; dispatch(k, UP);
```

**失焦保护**：窗口失焦（Alt+Tab）时，强制把所有 keyState 置 false 并调用所有 strategy 的 `onReset()`——否则会出现"松手了但游戏里还在往前跑"的经典 bug，摇杆卡死。这一条必须在 M2 第一天就做。

### 5.2 click / click_twice（普通点击、双击）

最简单，但有两个细节：

- `pressMs`：down 与 up 之间的间隔，默认 40ms。**太快（<16ms）部分游戏识别不到**，太慢会被判定为长按。做成可调，默认给 40ms。
- 双击：两次 down-up，间隔建议 60~100ms，同样可调。

### 5.3 steering（摇杆 / 方向键走位）★ 手感核心

**算法**（每 tick 或每次按键变化触发一次）：

```
vx = (right?1:0) - (left?1:0)
vy = (down?1:0)  - (up?1:0)          // 屏幕 y 轴向下为正
len = hypot(vx, vy)
if (len > 1) { vx /= len; vy /= len; }   // 归一化：斜向不加速
if (len < deadzone) { vx = 0; vy = 0; }  // 死区：轻触误判保护

targetX = center.x + vx * radius
targetY = center.y + vy * radius
```

**两种模式：**

| 模式 | 行为 | 适用 |
| --- | --- | --- |
| `hold`（默认，推荐） | 进入映射模式即 `DOWN` 在 center 并**保持手指不抬起**；按键时持续 `MOVE`；松开回到 center | 绝大多数游戏，延迟最低 |
| `tap`（兼容回退） | 每次按键触发完整的 `DOWN → MOVE → UP` | 少数会检测长按、或摇杆必须在 center 按下才响应的游戏 |

**为什么要 hold 模式**：FPS 走位是连续的，如果每次按键都重新 down，会有一次额外的手势建立开销，且部分游戏对"快速连续点击摇杆"响应不稳定。hold 模式下手指常驻，只有 move，最贴近真人手指按在摇杆上。

**移动步长限制**：单次 move 的位移不超过 `radius * 0.5`，超过则分多帧插值——防止瞬时大位移被游戏判为异常手势或触发"闪现"类误操作。

**回中**：松开全部方向键 → move 回 center（可用 `smoothing` 做 2~3 帧过渡，避免瞬间归零被识别为松手）。

### 5.4 view / crosshair（视角控制）★ 难度最高

这是"能不能像端游"的分水岭。

#### crosshair（虚拟准心）模式

1. 进入映射模式 → 鼠标指针锁定在窗口内（`ClipCursor`）+ 隐藏系统光标 + **OSD 绘制准心**。
2. 鼠标相对位移 `(dx, dy)` 累积到 `accum`。
3. 每个注入周期：从 `accum` 取出本周期位移，按灵敏度缩放，转成视角区域的一次拖拽。
4. 视角手指同样常驻（`hold`）：`DOWN` 在 `center` → 持续 `MOVE` → 退出映射模式才 `UP`。

```
// 每周期
stepX = accumX * sensitivity * (1 + accel * speedFactor)
stepY = accumY * sensitivity * (1 + accel * speedFactor)   // invertY 时取负
accum -= step                                  // 取走本周期的量，避免累积漂移
newPos = clamp(lastPos + (stepX, stepY), center ± radius)
inject(MOVE, viewPointerId, newPos)
```

**半径 clamp 是必须的**：视角拖拽不能无限累加，否则手指会滑出屏幕外被系统丢弃。主流做法是"相对滑动"——手指到达边界后回弹到 center 重新累积（即 recenter 策略），实现上：若 `|newPos - center| > radius`，则注入一次回到 center 的 move 并继续。这个 recenter 要做得无感（在同一次 move 序列里完成），否则玩家会感觉视角"跳一下"。

#### drag（按住拖拽）模式

按住 `dragKey`（默认右键）→ DOWN → 跟随鼠标 MOVE → 松开 UP。适合 MOBA/回合制，FPS 玩家一般选 crosshair。

#### 灵敏度与加速度

- 默认线性（`mouseAccel = 0`），FPS 玩家多数偏好线性。
- 加速度 >0 时启用曲线：慢速精细、快速大范围。提供 0~1 滑杆 + 实时预览。
- 灵敏度要区分"水平/垂直"可选，部分玩家要不同的 Y 轴速度。

### 5.5 fire（射击 / 连点）

- `hold: true` → 按下持续（最常用），`pos` 点常驻手指。
- `repeatMs > 0` → 连点模式，按固定间隔 down-up。**必须限最小值**（建议 ≥ 50ms），避免做成变相连点外挂。
- 与 view 共存：开火手指与视角手指是**两个不同 pointer**，互不影响（见 5.8）。

### 5.6 smart_cast / cancel_cast（智能施法 / 取消施法）

MOBA 刚需：按下技能键 → 显示技能范围 → 拖动选择方向 → 抬起施放；拖到取消区则取消。

```
onKeyDown: pointer DOWN 在技能键 pos
onTick:    若 aim == "view"，方向跟随 view 的当前指向 → MOVE 到 pos + dir*range
onKeyUp:   若指针在 cancelZone 内 → MOVE 到取消区再 UP（触发取消）
           否则 → UP 在当前位置（触发施放）
```

### 5.7 macro（宏按键）

时间轴步骤：

```jsonc
"steps": [
  { "act": "click", "pos": {...} },
  { "act": "wait",  "ms": 60 },
  { "act": "swipe", "from": {...}, "to": {...}, "ms": 120 },
  { "act": "key",   "code": "KeyF" }     // 触发另一个映射项
]
```

**硬性约束（合规红线，不可配置绕过）**：

| 约束 | 值 |
| --- | --- |
| `loop` 默认 false；置 true 时必须绑定"持续按住" | 松键即停 |
| 单次宏最短间隔 `minIntervalMs` | ≥ 200ms（默认） |
| 宏内不得包含图像识别、条件分支、读内存 | 结构上不支持 |
| 宏步骤数上限 | ≤ 32 |

引擎在执行 macro 时，**按键松开立即中止**剩余步骤并归位所有 pointer。

### 5.8 PointerPool：多指并发管理

同时按住"W 走位 + 鼠标转视角 + 左键开火 + Q 技能"是常态，需要 4 个独立手指。

```
ACTION_DOWN          → 第一个手指
ACTION_POINTER_DOWN  → 第 2~N 个手指（带 pointerId，需正确填 pointerIndex）
ACTION_MOVE          → 批量更新（一次事件可带多个 pointer 的坐标）
ACTION_POINTER_UP    → 抬起某一个（其余保持）
ACTION_UP            → 最后一个
```

**必须处理的坑（scrcpy 实现里真实踩过）**：

1. **pointer id 泄漏**：注入 down 后如果没有对应的 up，id 会被长期占用，后续触摸全部失效。必须有 id 池 + 超时回收（≥5s 无活动强制 UP）。
2. **MOVE 事件合并**：同一注入周期内多个手指都有位移 → 合成**一个**多指 MOVE 事件发送，而不是 N 个单指事件。既降带宽又保证游戏看到的是同一时刻的多指状态（分别发送会被识别为抖动）。
3. **index 与 id 不是一回事**：`pointerIndex` 是当前事件内的下标（会变），`pointerId` 是手指的稳定标识。混淆会导致多指乱跳。
4. **onReset 全覆盖**：失焦、断连、切换模式、切换脚本，都必须遍历池子把所有 active 手指 UP 掉。

### 5.9 其他类型速查

| 类型 | 实现要点 |
| --- | --- |
| drag（拖拽滑动） | 固定起止点，按 `durationMs` 分帧插值注入（默认 120ms，采样 8~12 个点） |
| swipe_direction（方向滑动） | 八方向 + 自定义距离，`durationMs` 建议 200~400ms（太快不触发） |
| sliding_attack（滑动攻击） | 滑动序列 + 攻击键 pointer 并行 |
| right_click_move（右键行走） | 点击坐标 → 与 steering center 求向量 → 转成 steering 输入 |
| view_extend（视野扩展） | 窗口渲染比例/裁切配置，不产生输入事件 |
| observe（观察视角） | 限定区域拖拽，pointer 在小地图范围内 clamp |

## 六、注入节奏与延迟控制

### 6.1 注入频率

| 场景 | 建议 injectHz |
| --- | --- |
| 视角移动（FPS） | 120（与高刷屏对齐） |
| 摇杆走位 | 60~90 |
| 普通点击 | 事件驱动，无需固定频率 |

过高的注入频率不会更跟手，只会让设备端 `injectInputEvent` 堆积、反而增加延迟。引擎按 **item 类型**分别节流：视角走高频，摇杆走中频，点击走事件驱动。

### 6.2 延迟预算（本模块内部）

| 环节 | 预算 |
| --- | --- |
| Raw Input 采集 | < 1ms |
| 队列传递 | < 1ms |
| 映射计算（查表 + 向量合成） | < 1ms |
| 序列化 + 发送 | 1~3ms |
| 设备端注入（server 侧） | 5~15ms |
| **本模块合计** | **≤ 15ms**（不含投屏画面延迟） |

### 6.3 背压与丢帧

队列满时：**丢弃最老的鼠标 move**（视角场景宁可丢中间帧也要保最新位置），但**绝不丢 down/up**（丢一次就是手指卡死）。这是明确的优先级策略。

## 七、编辑器设计（所见即所得）

### 7.1 交互流程

```
① 连接设备并启动投屏，进入游戏到目标界面
② 打开映射编辑器 → 画面半透明覆盖一层编辑层
③ 从右侧"控件面板"拖一个类型到画面上 → 落点即相对坐标
④ 右侧属性面板调参数（键位、半径、灵敏度、时长…）
⑤ 点"试玩" → 实时生效，可边玩边调
⑥ 保存 → 生成 JSON，自动关联游戏包名
```

### 7.2 关键能力清单

| 能力 | 说明 |
| --- | --- |
| 帧冻结取点 | 游戏画面在动，取点困难 → 提供"冻结当前帧"再标坐标 |
| 网格吸附 + 对齐辅助线 | 摇杆/按钮常对称分布，吸附到已有控件的水平/垂直线 |
| 多选批量移动 | 整组 UI（如技能栏四个键）一起挪 |

| 屏幕比例模拟 | 编辑器可切 16:9 / 19.5:9 / 20:9 预览，检查键位在异形屏是否越界 |

## 八、兼容性与回退

### 8.1 游戏屏蔽模拟注入

部分游戏会检测非物理触摸源。回退链：

```
SDK 注入 (injectInputEvent)
   ↓ 失效
HID 模式（把 PC 键鼠伪装成 USB 物理键鼠，scrcpy v1.23+ 支持）
   ↓ 仍失效
标记该游戏为"不兼容"，写入众包清单
```

HID 模式同样是走 USB 的，与本产品"只做有线"的路线天然契合，是本方案相对无线方案的一大优势。

**注意**：HID 模式下输入以物理设备方式呈现，坐标体系可能不同（绝对坐标设备），需要引擎在 HID 模式下切换坐标输出方式——这点在 M3 做 HID 时一并处理。

### 8.2 需要众包维护的清单

- 摇杆 `hold` vs `tap`：哪些游戏必须 `tap`
- `pressMs` 有效区间：部分游戏 <30ms 点不动
- 视角 `radius` 有效值：不同游戏视角区域灵敏度差异大
- 是否必须开"USB 调试（安全设置）"：按机型记录

这份清单做成公开可编辑的文档/仓库，是社区参与感的重要来源。

## 九、合规红线（引擎层面的硬约束）

| 项 | 引擎实现 |
| --- | --- |
| 无自动瞄准 | 引擎不提供"识别敌人→移动准心"的能力，输入只能来自用户键鼠事件 |
| 无图像识别决策 | 引擎不接入画面帧数据做判断（架构上隔离：映射引擎拿不到视频帧） |
| macro 限速 | `minIntervalMs ≥ 200`、步骤数 ≤ 32、`loop` 必须绑定持续按键 |
| 连点限速 | `repeatMs ≥ 50` |
| 无内存/协议访问 | 无相关接口 |

**架构上隔离是最好声明**：让映射引擎**在代码层面拿不到视频帧**，就从根本上不可能实现自动瞄准——这既是合规保障，也是被质疑时最有力的说明。

## 十、测试方案

### 10.1 单元测试（无需设备）

| 用例 | 验证点 |
| --- | --- |
| 向量合成 | 四键组合 → 归一化正确，斜向不超速（\|v\| ≤ 1） |
| 死区 | 微小输入被过滤，边界值正确 |
| 坐标转换 | 含黑边/拉伸/旋转四种组合，正反变换可逆，误差 < 0.5% |
| recenter | 视角手指到达边界后回弹，位移连续无跳变 |
| pointer 池 | 并发 4 指分配/回收，超时强制释放，无泄漏 |
| 失焦归位 | 模拟 Alt+Tab，所有 keyState 清空、所有 pointer UP |

### 10.2 集成测试（真机 + 真实游戏）

- 每种映射类型至少 1 个真实游戏可玩用例。
- **跨分辨率一致性**：同一份键位在 720P / 1080P / 2K 三台设备上，点击命中同一 UI 元素。
- **并发压测**：摇杆 + 视角 + 开火 + 技能同时操作 5 分钟，无手指卡死、无 id 泄漏。
- **长时间**：连续游戏 2 小时，无内存增长、无延迟劣化。
- **失焦/断连**：Alt+Tab、拔线重插各 20 次，恢复后无残留手指。

### 10.3 手感测试（主观但必须有）

组织 5~10 名 FPS 玩家盲测，与 TC Games VIP 做 A/B，重点问三件事：**转视角跟不跟手、走位有没有迟滞、连续操作会不会卡指**。
